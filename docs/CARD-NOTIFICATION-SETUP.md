# 카드 결제 알림 자동 입력

카드를 쓰면 오는 **결제 알림(카톡 알림톡 / 문자)** 을 폰이 자동으로 앱에 보내고,
앱이 금액·가맹점·날짜·결제자·분류를 채워 가계부에 등록한다.

```
카드 결제 → 카톡 알림 → 폰(MacroDroid) → 서버 → 가계부
                                          ↳ 애매하면 Inbox
```

---

## 1. 서버 준비 (한 번만)

### 1-1. DB

Supabase → SQL Editor 에서 순서대로 실행.

| 파일 | 내용 |
|---|---|
| `054-card-notifications.sql` | 알림 수신 로그 + 중복 방지 |
| `055-card-notifications-alias.sql` | 카드 별칭(토스뱅크·온누리용) |
| `056-notify-requests.sql` | 들어온 요청 기록 (진단용) |

### 1-2. 비밀키

Vercel → Settings → Environment Variables 에 추가 후 **Redeploy**.

| Key | Value |
|---|---|
| `CARD_NOTIFY_SECRET` | 길고 무작위한 문자열 |

미설정 시 엔드포인트는 503 으로 닫혀 있다.

---

## 2. 폰 설정 (MacroDroid, 무료)

### 2-1. 권한 — 이 4개가 전부다

1. **알림 접근 권한** 허용
2. **배터리 최적화 제외** (`설정 → 앱 → MacroDroid → 배터리 → 제한 없음`)
3. 카카오톡 **알림 켜기 + 메시지 내용 표시**
4. **폰 재시작 후 MacroDroid 한 번 열기**

> ⚠️ **4번이 실제로 가장 중요했다.** 삼성폰은 알림 접근이 "켜짐"으로 보여도 리스너가
> 죽어 있는 경우가 있고, 재시작 없이는 살아나지 않는다. 설정이 다 맞는데 아무것도
> 안 올 때는 대부분 이것이 원인이다.

### 2-2. 매크로

**발동** — `기기 이벤트 → 알림 → 알림 수신됨` 을 카드사 수만큼 추가 (여러 개면 OR)

| 애플리케이션 | 포함하는 텍스트 | 대상 |
|---|---|---|
| 카카오톡 | `승인` | 삼성카드 등 대부분의 카드사 |
| 카카오톡 | `체크카드 국내 결제` | 토스뱅크 |
| 카카오톡 | `온누리상품권` | 디지털온누리 |

> 카드번호(`1810`)로 걸면 그 카드 한 장만 잡힌다. 카드가 여러 장이면 `승인` 으로 건다.
> 조건 없이 카카오톡 전체를 보내면 개인 대화까지 넘어가므로 반드시 단어 조건을 건다.

**동작** — `웹 접속 → HTTP 요청`

| 항목 | 값 |
|---|---|
| 요청 방식 | `POST` |
| URL | `https://<앱주소>/api/transactions/notify?secret=<비밀키>` |
| 콘텐츠 유형 | `text/plain` |
| 본문 | `[notification]` (매직 텍스트 → "알림 텍스트") |

부부가 같이 쓰면 **두 폰에 똑같이** 설정한다. URL·비밀키도 동일하게 쓴다.
결제자는 "어느 폰이 보냈는지"가 아니라 **알림 내용**으로 정해지므로 폰을 구분할 필요가 없다.

## 3. 결제자·결제수단이 정해지는 방식

**결제수단**
1. 카드 끝 4자리(삼성) 또는 별칭(토스뱅크 `생활비카드`, 온누리 `온누리`)이
   결제수단 이름에 들어있는 것을 찾는다.
2. 한 장만 걸리면 그대로 쓴다 (사용자 설정 존중).
3. 여러 장이 걸리면(`주희 온누리` / `성진 온누리`) 알림 속 이름으로 가린다.

**결제자** — 우선순위
1. 연결된 카드의 주인 (설정 → 결제수단에서 지정)
2. **알림에 적힌 이름** (`김*진` → 이름에 `진` 이 들어간 구성원이 한 명일 때만)
3. 과거 같은 가맹점의 결제자
4. 첫 구성원

> 결제수단 이름에 **소유자 + 카드 끝 4자리**를 넣어두면 가장 정확하다. 예: `성진 삼성 4530`
> 설정에서 카드를 추가할 때 이름에 구성원 이름이 있으면 소유자가 자동 선택된다.

## 4. 분류 학습 — 한 번 정하면 다음부터 자동

같은 가맹점의 **가장 최근 확정 거래**를 보고 카테고리·결제수단을 그대로 적용한다.

- 학습 대상은 사용자가 **직접 확정한 거래만**. 시스템이 추측한 값을 다시 배우지 않는다.
- 분류를 바꾸면 그 즉시 새 값이 적용된다.
- 결제수단과 카테고리가 모두 채워지면 **Inbox 를 건너뛰고 바로 확정**된다.
- 학습이 적용된 건은 메모에 `이전 분류 적용` 이 붙는다.

`주식회사농가참신` 같은 법인 등록명은 키워드 사전으로는 못 잡으므로 학습이 유일한 방법이다.

## 5. 지원 카드사

| 카드사 | 규칙 | 특이사항 |
|---|---|---|
| 삼성카드 | `samsung-v1` | 카드 끝 4자리·결제시각 제공 |
| 토스뱅크 | `tossbank-v1` | '승인' 대신 **'결제'**, 끝자리 대신 **별칭**, **시각 없음** |
| 온누리상품권 | `onnuri-v1` | 시각 없음, 마지막 줄이 **잔액** |

**온누리 결제는 삼성카드도 함께 알린다.** 삼성 쪽은 가맹점이 없어 쓸모없으므로
`결제대금에 미포함` 등을 근거로 버리고, 가맹점이 있는 온누리 쪽만 등록한다. (이중 등록 방지)

**규칙이 없는 카드사**도 원문은 저장된다(`status='unparsed'`). 거래는 만들지 않는다 —
틀린 거래가 들어가는 것보다 안 들어가는 편이 낫기 때문. 아래 쿼리로 문구를 모아 규칙을 추가한다.

```sql
SELECT raw_text, created_at FROM card_notifications
WHERE status = 'unparsed' ORDER BY created_at DESC LIMIT 20;
```

## 6. 진단 — 안 될 때 여기부터

**모든 요청이 결과와 함께 기록된다.** "폰이 안 보낸 것"과 "보냈는데 서버가 버린 것"을
구분할 수 있다.

```sql
SELECT created_at, result, reason, left(raw_text, 80)
FROM notify_requests ORDER BY created_at DESC LIMIT 20;
```

| result | 뜻 | 조치 |
|---|---|---|
| `created(자동확정)` | 가계부에 바로 등록 | 없음 |
| `created(Inbox)` | Inbox 에 등록 | 분류 지정 (다음부터 자동) |
| `duplicate` | 이미 받은 결제 | 없음 (정상) |
| `unparsed` | 지원 안 하는 카드사 | 규칙 추가 |
| `ignored` | 카드 알림 형식 아님 | 폰 발동 조건 확인 |
| `unauthorized` | 비밀키 불일치 | URL 의 `secret` 확인 |
| **기록 자체가 없음** | **폰이 안 보냄** | 2-1 의 권한·재시작 |

> 거래를 삭제해도 `card_notifications` 의 중복방지 기록은 남는다. 같은 알림을 다시
> 보내도 `duplicate` 로 막히므로, 재등록하려면 해당 행을 먼저 지워야 한다.

## 7. 개인정보

- 폰에서 **단어 조건으로 거르는 것이 1차 방어선**이다.
- 서버는 `금액(원)` + `승인/취소`(또는 `결제/출금` + `카드/뱅크/은행/상품권`)가
  있는 문장만 받아들이고, 나머지는 **저장하지 않고 즉시 버린다**.
- `notify_requests` 도 카드 알림으로 인정된 것만 본문을 저장하고,
  아닌 요청은 **글자 수만** 남긴다.
